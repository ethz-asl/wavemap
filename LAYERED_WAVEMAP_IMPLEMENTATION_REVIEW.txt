LAYERED WAVEMAP IMPLEMENTATION REVIEW
=====================================

Date: 2026-08-07
Scope: Current layered-map core, persistence, ROS server/conversions, RViz,
       examples, and the proposed live voxel-update path.


1. CURRENT ARCHITECTURE
-----------------------

The current RosServer owns two distinct map instances:

1. occupancy_map_
   - Created by MapFactory from the existing "map" parameters.
   - Passed to Pipeline.
   - Receives the existing sensor/ray integration.
   - Published and saved through the original Wavemap interfaces.

2. layered_extension_.layered_map_
   - Constructed independently as ExampleLayeredMap.
   - Its continuousMap() is a typed HashedWaveletOctree whose voxel contains:
       occupancy + RGB + traversability
   - Its discrete bundle contains:
       semantic + changed
   - Published and saved through the layered interfaces.

Within the layered continuous map, occupancy, RGB, and traversability really do
share one wavelet octree. However, this layered octree is not the same object as
RosServer::occupancy_map_. There is currently no pointer/reference connection or
automatic synchronization between the two instances.


2. DOES LAYERED OCCUPANCY WORK LIKE ORIGINAL OCCUPANCY?
-------------------------------------------------------

Mechanically, yes:

- LayeredVoxel is VoxelData<ContinuousLayers, ContinuousLayersPolicy>.
- VoxelData stores occupancy as a FloatingPoint and supports the arithmetic
  required by the existing integrators and Haar transform.
- HashedWaveletOctreeT<LayeredVoxel> derives from MapBase.
- Existing experiments exercise ray-tracing and hashed-wavelet integration on
  the typed map.
- Occupancy-only updates preserve the additional continuous data.
- Continuous-layer replacement can preserve occupancy by applying a voxel
  update whose occupancy delta is zero.

Equivalent implementation does not automatically mean identical runtime map.
For two independent maps to produce matching occupancy, they must receive the
same measurements in the same order with equivalent:

- coordinate frame and poses;
- min/max range and measurement model;
- voxel resolution and tree height;
- min/max log-odds thresholds;
- pruning configuration and timing;
- update scheduling and concurrency behavior.

The active dt_architecture config aligns both grids at 0.25 m. The layered map
explicitly uses min_log_odds=-2, max_log_odds=4, and tree_height=6. The original
map relies partly on the normal map defaults because only type and resolution
are explicitly configured. These effective configs should be compared or made
explicit before claiming exact equivalence.

Most importantly, the current original sensor pipeline only receives
occupancy_map_. Therefore the layered occupancy field remains independent (and
usually unobserved/default) unless a layered file is loaded or it is populated
through another path.


3. HIGH-PRIORITY CORRECTNESS IMPROVEMENTS
-----------------------------------------

3.1 Decide and document the occupancy relationship

Choose one supported model explicitly:

A. Compatibility-first dual maps
   Keep original Wavemap untouched and keep layered occupancy independent.
   Clearly document that /wavemap/map and /wavemap/layered_map may disagree.

B. Dual integration
   Feed the same observations to the original and typed layered octrees.
   This duplicates computation and memory, and exact equivalence requires
   matched configs and deterministic update ordering.

C. Synchronize occupancy into the layered map
   Copy/reconstruct occupancy periodically or before layered publication.
   This is potentially expensive and requires a well-defined incremental sync.

D. One typed continuous map with a compatibility view
   Use the typed map as the integrated source and expose occupancy through the
   legacy MapBase/topic/service interfaces. This is architecturally cleaner but
   has the greatest risk of changing original behavior and needs extensive
   compatibility tests.

The current code behaves as A, but that behavior is implicit.

3.2 Add the missing live update path

Add example-specific ROS messages for the first implementation:

LayeredVoxelUpdate.msg:
  geometry_msgs/Point position
  float32 r
  float32 g
  float32 b
  float32 traversability
  int32 semantic
  bool changed

LayeredVoxelUpdateArray.msg:
  std_msgs/Header header
  LayeredVoxelUpdate[] updates

Add geometry_msgs to wavemap_msgs message-generation and package dependencies.

3.3 Reuse the existing continuous replacement helper

Use setContinuousLayersAtVoxel() from layered_voxel_updater.h. It computes the
difference between observed and stored continuous data, then applies:

  LayeredVoxel(0.f, data_update)

This preserves layered occupancy while replacing RGB and traversability. Avoid
adding a second replacement implementation with subtly different semantics.

3.4 Use the existing Wavemap position-to-index convention

Convert world positions with pointToNearestIndex(position,
1 / min_cell_width). Do not use a custom floor(position / resolution), because
Wavemap defines indices through its voxel-center convention and handles negative
coordinates accordingly.

3.5 Lock all access to the layered map

The live callback must update continuous and discrete layers while holding the
same mutex used by load/save/publish. Do not mutate through getLayeredMap(),
because that method returns an unprotected mutable reference.

Prefer a member function such as applyVoxelUpdates() that owns locking and
returns the publication stamp/result. Consider removing the mutable public
getter or replacing it with explicitly locked visitor/access functions.

3.6 Fix load concurrency

loadLayeredMap() currently copies layered_map_ before taking mutex_. Since the
LayeredMap copy contains a shared_ptr to the continuous map, concurrent update,
save, or publish operations can race with this initial copy/load workflow.
Protect the snapshot/replacement correctly, or load into a fresh map created
from a safely copied config without sharing mutable map storage.

3.7 Make reset behavior consistent

RosServer::clear() clears inputs, pipeline, and occupancy_map_, but does not
clear the layered map. Decide whether reset_map should also clear layered data.
If compatibility requires separate behavior, add a dedicated reset_layered_map
service and document the distinction.


4. LIVE UPDATE MESSAGE SEMANTICS TO DEFINE
------------------------------------------

Before implementing the subscriber, define these behaviors explicitly:

- Version 1 requires header.frame_id == configured world_frame.
- Reject an empty or mismatched frame; do not silently interpret it.
- No TF conversion in version 1. Add TF later as a separate feature.
- Validate positions and float fields with std::isfinite.
- Define RGB range as [0, 1]. Decide whether invalid values are rejected or
  clamped; logging and stored behavior must agree.
- Define traversability range as [0, 1].
- Define valid semantic label values, including whether a sentinel means
  unknown/unobserved.
- Decide whether changed is an input observation or a value derived by comparing
  old and new data. It can remain explicit for the first pipeline experiment.
- All fields are currently mandatory and use replacement semantics.
- If several updates map to one voxel, apply message order and let the last valid
  update win, or deduplicate explicitly. Document the choice.
- Define whether one invalid update rejects the whole batch or only that entry.
  Skipping invalid entries with throttled warnings is practical for live input.
- Define maximum accepted batch size to prevent a malformed message from causing
  excessive latency or memory use.
- Publish once per accepted batch, never once per voxel.
- Preserve the incoming timestamp when publishing the resulting state where
  useful, rather than always replacing it with ros::Time::now().

Future messages may need per-field validity masks so a producer can update only
semantic, only RGB, etc. The first fixed message has no way to distinguish
"replace with zero/false" from "field not observed".


5. DISCRETE-LAYER IMPROVEMENTS
------------------------------

- The actual update method is setValue(), not set(). Use the existing API.
- Add an erase/set-unobserved operation. Currently a value can be set but there
  is no public way to make one voxel unknown again.
- Remove empty parent cells after erase support is added.
- setValue() expands and rebuilds the entire compressed parent cell on every
  voxel update. This is acceptable for 2x2x2 parents and initial validation,
  but batch updates should group observations by parent to avoid repeated work.
- Validate DiscreteCompressionConfig.block_height. Negative values and large
  shifts can cause invalid or overflowing side lengths/counts.
- Validate deserialized observed and exception offsets against the configured
  parent voxel count.
- Validate that every exception offset is also observed.
- Reject duplicate parent cells in ROS/file input instead of silently allowing
  later values to replace earlier values.
- Standardize serialized type names (currently examples use strings such as
  "int" and "bool") and consider stable versioned identifiers.
- Add equality/comparison helpers to make round-trip and update tests clearer.


6. CONTINUOUS MAP, THRESHOLD, AND PRUNING IMPROVEMENTS
-----------------------------------------------------

- Document that continuous replacement creates/updates wavelet coefficients and
  should be followed by thresholding according to a defined schedule.
- Decide when prune() runs for live updates. Pruning every message may be too
  expensive; never pruning can grow memory indefinitely.
- Verify that combined pruning weights cannot discard meaningful occupancy due
  to interactions with RGB/traversability scores.
- Add tests for updates at negative indices, block boundaries, and exact voxel
  boundaries.
- Add tests proving occupancy is unchanged after repeated continuous replacement,
  threshold, prune, save/load, and ROS round trips.
- Add tests for non-finite and out-of-range continuous values.
- Ensure both original and layered effective occupancy thresholds are explicit
  when equivalence is expected.


7. ROS PUBLICATION AND PERFORMANCE IMPROVEMENTS
-----------------------------------------------

- publishLayeredMap() serializes the complete continuous octree and all discrete
  cells. Publishing a full map after every high-rate update batch will become a
  CPU, allocation, bandwidth, and RViz bottleneck.
- For the first small experiment, one full publish per batch is acceptable.
- For real data, coalesce updates and publish at a configurable maximum rate.
- Add incremental/delta layered messages later, including block allocation and
  deletion semantics.
- Keep the existing full latched topic for new subscribers and explicit full-map
  requests.
- Avoid holding the map mutex longer than necessary, but do not serialize from
  mutable map storage without a safe snapshot strategy.
- Add counters/timing for received, accepted, skipped, and deduplicated updates;
  update latency; serialization time; message bytes; and publication rate.
- Make subscriber queue size and publish rate configurable.
- Add backpressure/drop behavior instead of allowing stale update batches to
  accumulate.
- Consider an AsyncSpinner only after map locking and callback ordering semantics
  are explicitly safe.


8. ROS CONVERSION ROBUSTNESS
----------------------------

- LayeredVoxelRosConverter assumes fixed layer positions and directly indexes
  arrays without validating names, types, layer counts, or value lengths.
  Malformed messages can cause out-of-range access.
- Validate continuous layer schema before reading cell data.
- Validate expected RGB value count (3 per coefficient) and traversability count
  (1 per coefficient).
- Return structured conversion errors rather than only bool where practical.
- Validate wavelet node count/stack consistency and child bitsets during map
  reconstruction.
- Validate discrete layer ordering or resolve layers by name. The current bundle
  conversion requires exactly the expected count and positional order.
- Add message/schema versioning for forward compatibility.
- Add fuzz or malformed-message tests for every conversion entry point.


9. SERVER AND PACKAGE STRUCTURE IMPROVEMENTS
--------------------------------------------

- wavemap_ros and the RViz plugin directly include configuration headers from
  examples/cpp/digital_twin/common through private include paths. Installed
  packages may not contain those example headers, making the feature fragile
  outside this source workspace.
- Move the supported example layered types/converters into an installable
  library/package, or create a dedicated wavemap_digital_twin package.
- Keep generic LayeredMap, I/O, and conversion mechanisms in library/interface
  packages; keep example schema policy in the example/digital-twin package.
- Avoid hardwiring ExampleLayeredMap construction inside RosServer long term.
  Use a factory/extension registration mechanism or an explicitly optional
  digital-twin server component.
- Validate layered_map configuration with the same rigor as existing ConfigBase
  configurations, including compression and threshold constraints.
- Improve startup logging to report effective layered resolution, tree height,
  thresholds, schema, update topic, and occupancy relationship mode.


10. RVIZ IMPROVEMENTS
---------------------

- The RViz LayeredMap display is also compiled against example configuration
  headers. Separate generic display mechanics from example continuous-layer
  color policies.
- Validate incoming schemas and array lengths before reconstruction.
- Avoid rebuilding all geometry unnecessarily when only a small layer delta is
  received (after delta transport exists).
- Add limits/decimation for very large maps to prevent CPU/GPU memory exhaustion.
- Expose voxel count, message size, reconstruction time, and rejected-message
  errors in display status.
- Preserve the dynamic layer dropdown, but handle removed/renamed layers without
  retaining an invalid selection.
- Test topic and file modes with empty maps, huge maps, malformed maps, frame
  changes, and repeated load/unload cycles.


11. PERSISTENCE AND SCHEMA IMPROVEMENTS
--------------------------------------

- Add formal unit tests for .lwvmp round trips, incompatible schemas, truncated
  files, corrupt counts, invalid compression offsets, and unsupported versions.
- Apply bounds before allocating from file-provided counts to avoid excessive
  memory allocation on corrupt files.
- Include an explicit format version and migration policy if not already fully
  enforced by the current header/schema implementation.
- Consider checksums for large files or sections so corruption is detected early.
- Ensure save is atomic: write a temporary file, flush/close successfully, then
  rename into place so failure cannot destroy the previous valid map.
- Document endianness and numeric representation if files must be portable.


12. TESTING IMPROVEMENTS
------------------------

Many current checks are standalone experiment executables. Preserve them, but
promote the critical behavior into automated unit/integration tests:

- original occupancy integration remains unchanged when layered support is off;
- enabling the extension does not alter original topics/services/results;
- typed layered occupancy matches scalar occupancy under identical config and
  identical observation sequences;
- continuous replacement preserves occupancy;
- occupancy integration preserves RGB/traversability;
- discrete values remain sparse/unknown correctly;
- negative-coordinate compression and indexing;
- continuous and discrete save/load round trips;
- ROS message round trips and malformed-input rejection;
- frame mismatch and invalid-value behavior;
- concurrent update/save/load/publish/reset behavior;
- live publisher -> server -> LayeredMap topic -> RViz/converter test;
- save-after-live-update and reload verification;
- bounded publication rate and queue behavior under load;
- compatibility build with layered support disabled.


13. RECOMMENDED IMPLEMENTATION ORDER
------------------------------------

Phase 1: Safe proof of live updates

1. Define and document the occupancy relationship (retain dual-map behavior for
   compatibility during this phase).
2. Add the two example-specific update messages and dependencies.
3. Add a validated ROS-to-observation converter using pointToNearestIndex().
4. Reuse setContinuousLayersAtVoxel() and DiscreteLayer::setValue().
5. Add a mutex-protected update method/subscriber inside the extension.
6. Publish one full map per small test batch.
7. Add the publisher experiment.
8. Add automated occupancy-preservation and end-to-end tests.
9. Test live RViz and save-after-update.

Phase 2: Correctness and operational hardening

1. Fix load/reset/accessor concurrency and semantics.
2. Add strict message and deserialization validation.
3. Add publish throttling/coalescing and diagnostics.
4. Make original/layered effective configs explicit and comparable.
5. Move example headers out of private cross-package include paths.

Phase 3: Occupancy unification decision

1. Benchmark dual integration, incremental synchronization, and compatibility
   view approaches.
2. Select one based on CPU, memory, exactness, and backward-compatibility needs.
3. Implement it behind an explicit configuration mode.
4. Add equivalence and regression tests before changing defaults.

Phase 4: Generalization

1. Add optional/per-field updates and validity masks.
2. Add TF support.
3. Add schema-driven generic updates only after real producer requirements are
   known.
4. Add incremental layered publication and RViz application of deltas.


14. IMMEDIATE CONCLUSION
------------------------

The typed layered octree can perform occupancy integration similarly to the
original occupancy octree. The current server simply does not route the original
live integration into it. Keeping the original octree untouched is a valid and
useful compatibility strategy, but the relationship between the two occupancy
representations must be explicit to users and tests.

The safest next implementation is an example-specific, world-frame-only voxel
update subscriber that changes RGB, traversability, semantic, and changed while
preserving the layered occupancy field. Occupancy synchronization/unification
should be treated as a separate architectural decision, not accidentally mixed
into the first live-layer update patch.
