LAYERED LAYER POLICY AND STORAGE DESIGN NOTES
=============================================

Status
------
These are design decisions and deferred ideas. They are not requirements for
the current occupancy + reflectivity + class example and are not implemented
unless explicitly stated otherwise.


1. Layer semantics and storage are separate concepts
----------------------------------------------------

The public meaning of a layer must not determine its storage automatically.
A future layer definition should independently select:

  * Value type: float, integer/category, bool, RGB, vector, structured state.
  * Update policy: replace, logical operation, voting, hysteresis, etc.
  * Storage policy: wavelet, majority + exceptions, sparse voxels, bit-packed
    booleans, direct structured storage, etc.
  * Pruning/compression policy.
  * Serialization/transport codec when the generic codec is insufficient.

The intended shape is conceptually:

  Layer<Value, UpdatePolicy, StoragePolicy, PruningPolicy, Codec>

Compile-time templates are preferred so integration does not gain virtual-call
overhead.


2. Continuous and discrete are not a closed list of storage backends
------------------------------------------------------------------

The current continuous implementation is specifically suitable for numeric
state that supports meaningful addition, subtraction, scaling, wavelet
reconstruction, thresholding, and pruning.

The current discrete implementation uses spatial majority + exceptions.

Structured numeric information can require another backend even when it is
mathematically continuous. Examples include:

  * Unit surface normals.
  * Covariance matrices and NDT statistics.
  * Probability distributions or mixtures.
  * Multiple surfaces/hypotheses in one voxel.

Prefer storing additive sufficient statistics where possible. For example,
NDT data can store count, position sum, and outer-product sum, then derive mean
and covariance when queried. Coupled pruning is required so independent
thresholding does not create inconsistent or invalid reconstructed state.

Variable-length histories, graphs, connectivity, and per-frame metadata may
belong alongside the voxel map instead of becoming voxel layers.


3. Current meaning of majority + exceptions
--------------------------------------------

Majority + exceptions is a spatial storage/compression method. A compressed
parent stores:

  * Its dominant child value.
  * Which child offsets are observed.
  * Explicit values for children that differ from the dominant value.

It is not an observation update policy and is not restricted to replacement.
For example, the logical output of replace, logical OR, hysteresis, or temporal
voting can all be spatially stored with majority + exceptions.

There are two different meanings of "majority" that must remain separate:

  * Temporal majority: observations over time vote for one voxel's value.
  * Spatial majority: nearby child values are compressed under one parent.


4. The changed boolean layer
----------------------------

Majority + exceptions is valid for a spatial changed/not-changed boolean,
particularly when changed voxels are rare among mostly false voxels.

A sparse or bit-packed boolean backend may eventually be more compact, but it
is an alternative storage policy, not a different semantic layer type.

If "changed" represents an event or history rather than persistent state, a
boolean alone may be insufficient. It may need a last-changed timestamp or a
separate event/history system.


5. Per-layer discrete storage policies (deferred)
-------------------------------------------------

The desired future map keeps heterogeneous side layers:

  class      -> MajorityWithExceptionsStorage<int>
  changed    -> MajorityWithExceptionsStorage<bool> or BitPackedBoolStorage
  object_id  -> SparseVoxelStorage<int>

Majority + exceptions should remain the default for backwards compatibility:

  DiscreteLayer<Value,
                UpdatePolicy,
                StoragePolicy = MajorityWithExceptionsStorage<Value>>

Required refactoring:

  1. Extract majority + exceptions into a standalone storage policy.
  2. Make discrete configuration, including block height, per layer.
  3. Define a storage contract for get, set, erase, batch updates, iteration,
     dirty-region tracking, and clearing only published dirty regions.
  4. Implement SparseVoxelStorage as a second backend to prove modularity.
  5. Decouple ROS and RViz from majority + exceptions internals.
  6. Provide a generic logical voxel patch and automatic visualization path.
  7. Allow optional optimized codecs for backends that should preserve their
     compression over ROS or on disk.
  8. Store backend identifier and format version in persistent files.

Users should not need custom ROS or RViz code for a normal custom storage
policy. Specialized codecs should only be necessary to preserve backend-
specific compression or hidden state.


6. Temporal majority with majority + exceptions (deferred)
----------------------------------------------------------

A true temporal majority requires per-voxel hidden integration state such as
vote counts. Keeping only the current winning integer is insufficient because
the history cannot be reconstructed from the winner.

The processing sequence would be:

  observations for one voxel
      -> update temporal vote state
      -> calculate current winner
      -> if winner changed, update logical class value
      -> spatially recompress that value using majority + exceptions
      -> mark/publish only the changed spatial parent

Vote-state changes should not dirty the visible class layer when its winner
does not change.

The architecture therefore needs a distinction between:

  * Public Value: the winning class ID.
  * Stored integration State: vote counts or another stability state.
  * Spatial StoragePolicy: how public class values are compressed.

If mapping must resume exactly after loading, hidden vote state must also be
saved. Saving only winners is sufficient for visualization and queries, but
not for resuming exact temporal voting.


7. Efficiency decision for temporal class stability
----------------------------------------------------

Full vote histograms are not the preferred default for the current geometric
forest classifier. They require multiple counters per voxel and additional
update work.

Lower-cost alternatives, in increasing complexity, are:

  * Replace/latest value.
  * Class plus one contradictory-observation hysteresis counter.
  * Candidate class plus confidence counter (streaming approximate majority).
  * Two candidates and two counters.
  * Decaying class confidence.
  * Full per-class temporal vote histogram.

For this project, if replacement later proves too noisy, the preferred next
experiment is a compact state:

  StableClassState {
    int class_id;
    uint8_t confidence;
  }

This has constant memory independent of the number of classes, cheap updates,
and should reduce class changes and discrete patch traffic. Full temporal
majority remains an optional advanced policy, not the default.


8. Suggested future implementation order
-----------------------------------------

  1. Formalize custom stateless update-policy requirements.
  2. Add explicit public Value versus stored State support.
  3. Extract the existing majority + exceptions backend.
  4. Add per-layer storage configuration.
  5. Implement and test one second discrete backend.
  6. Introduce storage-independent logical patches for generic ROS/RViz use.
  7. Add optional optimized transport and file codecs.
  8. Experiment with compact class hysteresis only if replacement is too
     unstable in real mapping tests.
